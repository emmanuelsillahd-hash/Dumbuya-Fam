## 2. Authoritative Database Architecture Assessment

### 2.1 Why `data/familyos-shared-store.json` Is Unsuitable for Production
Currently, `server.ts` (`lines 18–20, 129–144`) persists all state in a local flat JSON file (`data/familyos-shared-store.json`) using `fs.readFileSync` and `fs.writeFileSync`. This is unsuitable for production for four concrete technical reasons:
1. **Concurrent Write Race Conditions (Lost Updates)**: Simultaneous requests (`loadStore()` -> mutate in memory -> `saveStore()`) overwrite each other without row-level locking or ACID isolation.
2. **Lack of Atomic Multi-Entity Transactions**: Recording an expense updates `accounts`, `budgets`, `transactions`, and `auditEvents`. A crash or error mid-write leaves the JSON file partially mutated or corrupted.
3. **Ephemeral Container Filesystem on Cloud Run**: When deployed to Google Cloud Run (`europe-west2.run.app`), the container filesystem is ephemeral. Container restarts, autoscaling, or redeployments wipe `data/familyos-shared-store.json`, causing total data loss.
4. **Full-Dataset Serialization Overhead**: Every single API read or write parses and serializes the entire database payload in memory (`O(N)` memory and I/O blocking the Node.js event loop).

### 2.2 Evaluation of Authoritative Shared Database Options
Because inspection of `package.json`, `.env.example`, and `src/` confirmed that **no external Lovable/Supabase backend exists in the workspace**, we evaluated the three viable database architectures available within Google AI Studio & Android:

| Criteria | Option A: Firebase Firestore + Firebase Auth (Recommended) | Option B: Cloud SQL for PostgreSQL + Firebase Auth | Option C: Embedded SQLite (`better-sqlite3`) on Express Container |
|---|---|---|---|
| **Existing Codebase Alignment** | **Highest**: Android (`android/app/build.gradle.kts:110–113`) *already* includes `firebase-bom`, `firebase-auth-ktx`, `firebase-firestore-ktx`, and `firebase-storage-ktx`. `FirebaseAuthRepository.kt` is already written for Firebase Auth. | **Medium**: Requires introducing Drizzle ORM + PostgreSQL schema migrations on the Node backend while Android uses Room + REST. | **Low**: Fixes local ACID/concurrency, but **still loses all data** on Cloud Run container redeploy/scale-to-zero because container disk is ephemeral. |
| **Shared Identity & Auth** | **Native Unified Identity**: Firebase Authentication provides one consistent identity system (`uid`, ID tokens) across both the React Web App and the Android Kotlin App. | Uses Firebase Auth for identity + PostgreSQL for storage. | Requires custom JWT or external auth service. |
| **Cost & Infrastructure Constraints** | **Generous Free Tier (Spark/No-Cost Tier)**: Serverless scale-to-zero, 50,000 free reads/day, 20,000 free writes/day, 1 GiB storage at $0 cost. Native AI Studio provisioning via `firebase-integration-rpc`. | Scale-to-zero Developer edition available in AI Studio, but relational connection pooling adds overhead for mobile sync queues. | Free, but **not persistent across Cloud Run deployments**. |
| **Cross-Platform Sync & Security** | Supports both server-authenticated Express `/api/v1/*` transactions (for complex atomic financial ledger operations) and strict `firestore.rules` RBAC enforcement. | Enforced solely via Express `/api/v1/*` middleware. | Enforced solely via Express `/api/v1/*` middleware. |

### 2.3 Recommended Target Architecture
We recommend **Option A: Firebase (Firestore + Firebase Authentication) combined with the Express `/api/v1/*` Transaction Gateway**:
- **Android Application**: Kotlin + Jetpack Compose with local SQLCipher-encrypted Room (`FamilyOSDatabase` v3, 39 entities) as the offline-first local cache and transactional queue.
- **Web Application**: Existing React application in `/src/` connected to the same authoritative family records.
- **Authentication**: **Firebase Authentication** (Email/Password & Google Sign-In) across both Web and Android, issuing verifiable Firebase ID tokens (`uid`, `email`).
- **Authoritative Shared Database**: **Cloud Firestore** provisioned in the workspace's Firebase project, accessed both via the hardened `/api/v1/*` Express backend (enforcing server-side RBAC, idempotency, and atomic integer-cent ledger batches) and protected by strict `firestore.rules`.
- **Fallback / Zero-Downtime Migration Guard**: A storage repository abstraction (`AuthoritativeStoreAdapter`) in `server.ts` that writes atomically to Firestore when provisioned and maintains deterministic local snapshot backup in `data/backups/` with full import/export verification.

## 6. Consolidated Priority Classification (P0–P3)

### P0 — Critical Production Blockers (Must Fix in Stage 3.2)
- **P0-1 (Authoritative Database & Concurrency)**: Replace unindexed flat-file `data/familyos-shared-store.json` as primary storage with an ACID/transactional authoritative store (Firebase Firestore + atomic local backup store with mutex serialization) so concurrent requests and container restarts never corrupt or lose family records.
- **P0-2 (Server-Side Authentication & Untrusted Role Injection)**: Remove all trust in client-supplied `req.body.actorRole`, `familyId`, and `memberId`. Require verified authentication headers (`Authorization: Bearer <token>`) and resolve the caller's `userAccountId`, `familyId`, `memberProfileId`, `role` (`OWNER`, `ADMIN`, `MEMBER`, `CHILD`, `GUEST`), and guardian links exclusively from server-side membership records on every `/api/v1/*` endpoint.
- **P0-3 (Multi-Family Tenant Isolation & Minor Health Privacy)**: Enforce strict `:familyId` membership verification on `GET /api/v1/workspace/:familyId` and filter out restricted minor medical/wellbeing records (`wellbeing_profiles`, `health_allergies`, `health_medications`) unless the authenticated caller is `OWNER`, `ADMIN`, or a verified legal guardian in `guardian_relationships`.
- **P0-4 (Financial Transaction Idempotency & Duplicate Reversal Index)**: Enforce mandatory `idempotencyKey` (`X-Idempotency-Key` / `req.body.idempotencyKey`) on `POST /api/v1/finance/transaction` and `POST /api/v1/finance/reverse`. Add duplicate-reversal check in Android `FinanceRepositoryImpl.reverseTransaction()` (`Stage3RepositoriesImpl.kt:68–90`) and `Stage3Daos.kt` so a transaction can never be reversed twice locally or remotely.
- **P0-5 (Full Cross-Platform Bi-Directional Sync for All Modules)**: Extend `server.ts` `/api/v1/sync/push` and `/api/v1/workspace/:familyId` (plus `GET /api/v1/sync/pull`) to persist and synchronize all required cross-platform entities (`family_workspaces`, `family_members`, `family_memberships`, `guardian_relationships`, `tasks`/`checklists`, `chores`, `meal_plan_entries`/`recipes`/`grocery_list_items`, `financial_accounts`/`transactions`/`budgets`, `wellbeing_profiles`/`allergies`/`medications`, `emergency_contacts`/`plans`), and wire `HttpRemoteSyncGateway` + `SyncRepositoryImpl` to both push pending operations and pull remote delta updates.

### P1 — High-Priority Security & Sync Hardening
- **P1-1 (Server-Enforced Conflict Resolution Policies)**: Implement server-side handlers in `/api/v1/sync/push` for `EVENT_BASED_MERGE` (additive task/checklist completion), `APPEND_ONLY_LEDGER` (immutable financial transactions, adjustments via reversal only), `SERVER_AUTHORITATIVE` (membership/role changes restricted to `OWNER`/`ADMIN`), and `TOMBSTONE_SOFT_DELETE` (`isDeleted = true` propagation).
- **P1-2 (Offline Membership Revocation Quarantine)**: Enforce active membership status (`status === 'ACTIVE'`) on `/api/v1/sync/push`; return `403 MEMBERSHIP_REVOKED` when a revoked member attempts to sync queued offline mutations, and transition the local `sync_queue` item to `QUARANTINED_UNAUTHORIZED` in `SyncRepositoryImpl`.
- **P1-3 (Private Reflection Journal Isolation)**: Enforce `is_private` ownership check on `reflection_journals` so personal private entries are only readable/writable by their creator (`member_id` linked to authenticated `user_account_id`), while shared entries are visible to active family members.

### P2 — Medium-Priority Reliability & Operational Hardening
- **P2-1 (Deterministic Backup, Migration & Rollback Tooling)**: Add automated backup snapshot creation before any store migration, SHA-256 checksum verification, and rollback restoration endpoint/script.
- **P2-2 (CI Pipeline Expansion)**: Add a backend & web verification job (`npm run lint`, `npm run build`, and automated security/cross-platform integration test suite) alongside the Android jobs in `.github/workflows/android.yml`.

### P3 — Low-Priority Polish
- **P3-1 (Vite Config Warning)**: Replace `__dirname` with `import.meta.dirname` in `vite.config.ts:11` to eliminate the Vite 8 native config loader warning observed during `npm run build`.
